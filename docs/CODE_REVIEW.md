# 代码审查标准与流程

适用 `:desktop` 与 `:engine-probe`。本文件只管「怎么审」，编码规范本身仍以 `AGENTS.md` 为准，两处冲突以 `AGENTS.md` 为准。

判据一律可判定：每条都能回答「过 / 不过」，不接受「注意代码质量」这类无法执行的表述。

## 一、设计依据

审查形态由三项现状决定，不是照搬通用流程：

1. **无静态检查与 CI**：仓内无 detekt / ktlint / spotless，无 workflow 文件。格式、未使用导入、空 catch 这类机械错误目前全靠人眼，人的注意力被低价值问题耗尽，真正的并发与安全问题反而漏掉。
2. **提交粒度失控**：近 30 次提交中 9 次改动 ≥5 个文件，单次最多 10 个，且一个提交常混多件事。审查者拿不到改动意图，无法判断「改得对不对」。
3. **超长文件使局部审查失效**：`VeneraDesktopLargeScreen.kt` 9550 行，另有 4 个屏文件 2400 行以上。改动一处无法推断波及面。

对应结论：机器先拦机械错，作者自查意图与验证，人工只审前两层判不了的部分。

## 二、三层防线

### L1 机器护栏（0 人力，当前缺失）

未落地，按此顺序补：

| 顺序 | 工具 | 拦什么 | 备注 |
|---|---|---|---|
| 1 | ktlint | 格式、导入顺序、未使用导入 | 只开 `ktlint_official` 规则集，不引入风格争论 |
| 2 | detekt | 空 catch、过长函数、过大类、`!!`、重复代码 | 阈值按第三节「规模」取值，首次接入用 baseline 冻结存量 |
| 3 | `:desktop:compileKotlin` + `-Werror` 分阶段 | 未使用变量、废弃 API | 先只对新增文件开，避免一次性红成一片 |

接入原则：**存量冻结，增量拦截**。不要求一次清空历史欠账，只保证新增代码不再恶化。

### L2 作者自查（提交前，必做）

作者在提交前逐项过第六节清单，并把读数贴在提交正文或审查请求里。缺读数的提交不进 L3。

### L3 人工审查（按风险分档）

见第三节。审查者只做三件事：判断意图是否成立、判断波及面是否可控、判断是否有机器测不出的隐患。

## 三、风险分档

按**改动面**定档，不按改动行数。取最高档。

| 档 | 触发面 | 审查强度 |
|---|---|---|
| **A 数据与安全** | `BusinessPorts` 及各族适配器、DAO 与数据库 schema、迁移逻辑、下载队列与写盘、JS 宿主与源更新、凭据与 cookie、网络代理与 CDP 桥、路径拼接 | 作者自查 + 一次独立复核，复核者须读懂数据层；必须附回滚方案 |
| **B 公共件与壳** | `ui/components/` 公共控件、主题与 token、壳层与路由、导航与返回栈、跨屏共享状态 | 作者自查 + 一名审查者 |
| **C 单屏与文案** | 单屏 UI、布局微调、图标、文案 | 作者自查即通过，审查者抽检 |

分档不清时取高档。A 档「独立复核」在单 AI 协作下指：换一个会话或隔时重读，不复用同一份上下文结论。

## 四、审查判据

每条标「不过」即为阻塞项，必须修完才能进下一环。

### 4.1 正确性与边界

- 不过：新增或修改的判据只覆盖正常路径，未说明空集合、空字符串、单元素、超长输入下的行为。
- 不过：空值兜底（`?: return`、`?: null`、`if (x == null) return`）落在关键路径上却没有一行读数。判据同 `AGENTS.md`「症状定位」第 2 条。
- 不过：`!!` 用于外部输入、解析结果、异步回包。
- 不过：异常被 `catch` 后静默吞掉，既不上报也不降级。

### 4.2 并发与协程

本仓 A 档高危面，逐条必查：

- 不过：同一状态有两个写入方，且未说明谁赢。典型形态是「盘上快照整体覆盖内存态」——盘上不含运行中态，覆盖即把运行中任务打回待办，造成并发写同一目录。
- 不过：`launch` 未绑定生命周期作用域，屏退出后仍在跑。
- 不过：共享可变状态跨协程读写，无锁、无原子、无单线程调度保证。
- 不过：`async` 并发启动后未在异常路径上收敛，失败时留下悬挂任务。
- 不过：为修并发问题而引入新的锁或闸，却未说明它保护的是哪个不变量、由谁释放。

### 4.3 资源与生命周期

- 不过：大图、文件流、原生句柄、CDP 连接在屏退出后仍持有。
- 不过：`DisposableEffect` / `remember` 的释放分支与申请分支不对称。
- 不过：缓存无上限或上限写死且无读数验证。

### 4.4 数据与迁移

- 不过：迁移用「表非空」判断是否已迁移——空壳表会骗过判据，导致旧数据永久不可见。必须用显式标记位。
- 不过：迁移不可重入，中途失败后重跑会写坏数据。
- 不过：schema 变更未说明旧库如何兼容，或兼容靠「用户重装」。
- 不过：写盘路径未做规范化校验，仅做字符串替换挡不住纯 `..`。

### 4.5 安全面

- 不过：路径拼接未走 canonical 化后比对根目录。
- 不过：本机监听端口（桥接、调试、CDP）无鉴权且无来源校验，窗口期内任意本机进程可连。
- 不过：日志、错误上报、崩溃读数中出现凭据、cookie、token、完整用户路径明文。
- 不过：脚本宿主放权扩大（`allowHostAccess` 放宽、新增导出成员）而无逐成员理由。
- 不过：第三方下载内容仅做语法校验就进入执行或覆盖层，未说明信任边界。

### 4.6 架构边界

判据直接引 `AGENTS.md`「架构边界」5 条，审查时只验结果：

- 不过：屏本体出现平台 import 或直接读写显示模式，绕开 `LocalUxPlatformServices`。
- 不过：桌面侧调用 `BusinessPorts.of`。
- 不过：共享内核吃进 ViewModel / Context 一类平台类型。
- 不过：为图省事在 `:desktop` 里复制共享层逻辑，造成两处口径。

### 4.7 规模与可读性

针对超长文件的渐进约束，不要求一次重构：

- 不过：在已超 1500 行的文件里新增顶层声明。只许拆，不许长。
- 不过：新增文件超 800 行而无拆分说明。
- 不过：新增函数超 60 行（Composable 放宽到 120，其结构长度由 Compose 决定）。超出须说明为何不能再分。
- 不过：一个提交混两件以上无关改动。审查者有权要求拆提交后再审。
- 不过：复制粘贴出的第二份实现，未说明为何不能抽公共件。

### 4.8 测试

- 不过：改动 A / B 档行为却无对应测试，且未说明为何不可测。
- 不过：修 bug 未附一个「修复前会失败」的测试，或未说明构造不出该场景的原因。
- 不过：测试依赖真实网络、真实时钟、真实用户目录绝对路径。
- 不过：把「点名跑了几个类」表述为「全量绿」。`AGENTS.md`「验证节奏」第 4 条为硬约束。
- 不过：为让测试变绿而放宽断言、加 `@Ignore`、改判据阈值，且未在提交正文说明。

### 4.9 注释与文案

判据同 `AGENTS.md`「代码注释」「UI 文案与设计语言」，审查时只验结果：

- 不过：注释复述代码在做什么，或写来历、日期、迭代编号。
- 不过：公开函数无 KDoc，或 KDoc 未写清每个参数该传什么。
- 不过：注释出现第三方软件名、其源码片段或原文注释。
- 不过：UI 出现拟人、比喻、文学修辞；主标题超 6 字、副标题超 15 字。

## 五、流程

```
改动 → 分档（第三节）
  ├─ C 档：自查清单 → 增量编译 → 提交
  └─ A/B 档：自查清单 → 增量验证（贴读数）→ 审查请求 → 审查结论
                ├─ 有阻塞项 → 修 → 重跑受影响的增量验证 → 复审
                └─ 无阻塞项 → 提交
```

硬性要求：

1. **审查请求必须带意图**：一句话说清「改了什么行为、为什么必须这么改」。写不出即说明改动未收敛。
2. **审查请求必须带读数**：跑了哪些点名的测试类 / 哪条编译命令，结果如何。空口「已验证」不接受。
3. **审查结论只有三档**：通过 / 有条件通过（列出必须修的阻塞项）/ 打回（说明方向性错误）。不写「建议优化」当结论——建议项单列，不阻塞。
4. **修完必须重跑受影响的增量验证**，不复用审查前的读数。
5. **A 档改动必须能回答回滚方式**：改坏了怎么退回，数据能否回退。

## 六、提交前自查清单

复制到提交正文或审查请求，逐项打勾：

```
[ ] 意图：一句话说清改了什么行为
[ ] 分档：C / B / A
[ ] 增量验证：跑了什么，结果如何（贴命令与读数）
[ ] 新增/修改行为有测试；修 bug 有修复前会失败的测试
[ ] 空值与异常路径有明确行为（兜底或上报，不静默吞）
[ ] 并发改动说明了状态写入方与不变量
[ ] 资源申请与释放对称
[ ] 无凭据/路径明文进日志与上报
[ ] 未在超长文件新增顶层声明
[ ] 本提交只做一件事
[ ] 注释与 UI 文案符合 AGENTS 规范
[ ] （A 档）附回滚方式
```

## 七、落地顺序

按此顺序推进，每一步独立可验证，不并行铺开：

1. **先补 L1**：接入 ktlint + detekt，用 baseline 冻结存量，只拦新增。此步完成后 L3 的格式类争论可直接消失。
2. **再固化分档**：把第三节的触发面写进提交模板，作者自行定档，审查者只在定档错误时纠正。
3. **然后压提交粒度**：先要求「一个提交一件事」，暂不要求拆历史。粒度改善后审查成本自然下降。
4. **最后治超长文件**：按 4.7 只堵增量，不排期大重构。等某个屏本身要重做时顺带拆。
